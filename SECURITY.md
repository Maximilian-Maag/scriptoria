# Security policy

Scriptoria runs scripts and holds their output: an audit trail that cannot be rebuilt, credentials
for a directory server, and SSH material for a machine that executes admin-written scripts. A
vulnerability here is worth reporting privately.

## Reporting

Use **GitHub's private vulnerability reporting** on this repository —
[Security → Report a vulnerability](https://github.com/Maximilian-Maag/scriptoria/security/advisories/new).
It is enabled, it is private, and it keeps the discussion attachable to the fix.

Please do not open a public issue, and do not include a live credential, key or transcript in a
report. A redacted example is enough.

What makes a report actionable:

- the path or route involved (`/api/runs/{id}/transcript`, the `/terminal` upgrade, a deployment
  script), and the commit you tested;
- the smallest sequence that shows the problem;
- what an attacker gains that they should not — a run's output, another area's script, a command on
  the script VM, the audit trail, a session;
- whether it needs a session, a particular group, or nothing at all.

## What is in scope

- **Authentication and sessions**: the LDAP bind, the session cookie, the session store.
- **Authorisation**: group-to-area resolution, and every route that answers from a session's area
  set. Seeing another area's script, run, output or audit entry is the failure that matters most.
- **The terminal stream**: the upgrade's authorisation, stdin routing, and the frame format.
- **Result files**: names and paths that reach a response header, a ZIP entry or a filesystem.
- **Command construction on the script VM**: quoting, interpreter selection, the closed vocabulary
  the execution target accepts.
- **The deployment layer**: unit files, the proxy configuration, and `infra/deploy/scripts/*`.
- **Dependencies**: an advisory with a path to exploitation in this code. A bare version-bump
  advisory is Dependabot's job, not a report.

## What is not a vulnerability

- **The development fixtures.** The dev SSH keypair (`make fixtures-key`), the seeded dev passwords
  and the LDAP fixtures exist to make the dev stack self-contained. They are accepted by the dev
  sshd and the dev directory only, and are regenerated by anyone who clones the repository.
- **The audit trail is append-only by design** — no update or delete path exists. That is a
  property, not a limitation to be worked around.
- **Missing features and wrong transaction shapes** in the open decisions on the requirements page.

## What to expect

There is no security response team and no SLA. A report will be read, and you will get an answer
saying what we intend to do; a fix lands on `dev` and reaches a release through the branch ladder
in `docs/guides/branching-and-ci.md`. Credit is given in the advisory unless you ask otherwise.

Fixes for anything that reaches a release branch go through the same checks as every other change:
the tests, the policy check, and — where the change touches `packages/core` — the mutation audit.
A fix without a test that fails before it is not a fix here.
